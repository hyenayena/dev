# dev

Development tools for a yena checkout, as a plugin (requires core 0.3.0+).

## Usage

- `dev` or `dev help` shows the help generated by core (arguments and options of every subcommand; `help dev test`). The policy of `dev` for the assistant is `confirm`.
- `dev test [suite…] [--file <path>]… [--name <pattern>]` runs every test suite (`host` first, then each `modules/*` that has a `test` script), or the named ones (in that order, repeats dropped). Progress shows in the console side panel as a braille bar per suite (one dot per test, eight per cell). `Esc` or `Ctrl+C` in the panel cancels the run, and so does the command context's `signal` (an assistant run that times out or is aborted cancels the test run; a signal already aborted cancels it at once). When it ends, a summary (counts, bars, failures) is printed into the transcript; a run through the console bridge (`ctx.signal` set: the assistant, a scheduler job) gets it without the bars. Test failures do not make the command fail; the summary reports them. Without a UI that can mount views the summary is printed at the end.
- `--file <path>` (repeatable, up to 50) runs only those test files instead of the script's globs, keeping its flags. A path is absolute, relative to the one named suite, or relative to the yena root; it must be an existing `.ts/.tsx/.mts/.cts/.js/.mjs/.cjs` file and goes to the deepest suite that holds it (a file under `modules/` never runs in `host`). With files, only their suites run. Example: `dev test claude --file tests/policy.test.ts`, or `dev check --file modules/claude/tests/config.test.ts --file tests/pm/run.test.ts`.
- `--name <pattern>` passes `--test-name-pattern` (a regular expression, 1 to 200 characters) to node; discovery is skipped then, so the bar grows as results arrive.
- `dev typecheck [suite…]` typechecks the host and every module with a `typecheck` script (or the named suites): at most 20 sanitized diagnostics per suite. `dev check` typechecks, then runs the tests only if the typecheck passed; with `--file` it typechecks only the suites the files belong to. `--file` and `--name` are refused by `dev typecheck`.
- One dev run at a time (`A dev run is already in progress`).
- From the terminal (`./yena dev …`, `ctx.headless`) a failure prints the summary and exits 1 (`<n> suite(s) failed`; a cancelled suite counts as failed). In the UI the commands only print.

## How it works
Which yena root is checked (`src/root.ts` `targetRoot`, asked on every run): the module's own root (`modules/dev/../..`), unless that is on a read-only filesystem (`EROFS`: the image at `/app`); then the working copy the host names in `BuildInfo.root.workCopy` (`/workplace/yena` by default, `mode dev [path]`), which must hold `package.json` and `modules/` (`No yena working copy in <path>`; on an older host without the field: `… names no working copy; update the host`). In dev mode the module already runs from the working copy, so its own root is that copy. Suites, `--file` paths, child cwd and `tsc` (the root's `node_modules/typescript`) all follow that root, so the working copy needs its own `./yena install`.


1. Each suite's `package.json` `test` script is parsed (`src/script.ts`), never run through a shell. Only `node [flags] --test [--test-* flags] <globs>` is accepted; shell metacharacters, unquoted globs and `--test-reporter*` are rejected (`Unsupported test script in <suite>`).
2. Discovery (`src/child/discover.ts`): up to 4 suites in parallel, each in a child that replaces `node:test` with a counting stub (`src/child/test-shim.ts`) and imports every test file without running a test body. This gives the planned total before the first real test runs. Files are counted as `max(1, registered tests)`, a file failing to import as 1. The child runs with a private `TMPDIR` that dev deletes afterwards. If discovery fails the bar grows as results arrive (`(unplanned)`).
3. Real run: suites run one after another with the script's own flags plus `src/child/reporter.ts`, which prints one NDJSON record per test. Anything else on stdout is ignored.

`dev typecheck` parses each suite's `typecheck` script (`src/typecheck.ts`), never through a shell: only `tsc` steps with `--noEmit` and `-p/--project <path>`, joined by `&&`; the tsc realpath must be inside the root; `--noEmit` is appended.

## Layout

`src/`: `index.ts` (plugin), `commands.ts`, `args.ts` (options), `suites.ts`, `script.ts`, `typecheck.ts`, `spawn.ts` (the only place that spawns), `runner.ts`, `store.ts` (outside React so the panel toggle keeps state), `layout.ts`, `summary.ts`, `format.ts`, `child/`, `ui/` (lazy: `TestView.tsx`, `mount.ts`). `kit.ts` and `ui/kit.ts` are the only files that import core (enforced by `tests/kit-boundary.test.ts`); `index.ts` never reaches react, ink or the kit UI statically.

Tests: `npm test` in this directory (they also run inside `dev test`, so the tests that spawn `node --test` rely on `spawnNode` removing `NODE_TEST_CONTEXT`). Fixtures in `tests/fixtures/` are named `*.fixture.ts` so the module's own glob does not pick them up.

## Residual risks

- Test scripts and test files of the other modules run with full rights, as they would from a shell. `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `NODE_TEST_CONTEXT` and `YENA_DEV_CHILD` (set in the yena process the dev launcher started; inherited, it would turn the host's overlay off in the tests) are removed from the child environment; other variables are inherited.
- Discovery imports test files, so top-level code of a test file runs (temp files go to the private `TMPDIR`; other side effects are not contained). Tests registered asynchronously or as subtests are not counted in the plan; the bar grows when more results arrive than planned.
- Children run in their own process group; cancel sends SIGTERM to the group and SIGKILL after 3 s, and an exit hook sends SIGKILL to live groups. In headless mode only, SIGINT/SIGTERM/SIGHUP handlers stop the children; in the UI no handlers are installed, so SIGTERM/SIGKILL on yena itself can leave a run alive until it ends.
- `-p` in a `typecheck` script may point outside the suite dir (tsc only reads that tsconfig); low risk.
- Flaky tests of other modules show up as failures.
